## What This Control Means

IPC surfaces such as intents, Binder/AIDL, content providers, and URL schemes that expose data or functions must authenticate callers and validate every input boundary.

## Why This Matters

Other apps and the user can reach IPC surfaces, so an unauthenticated export is an instant data or functionality leak.

## Main Security Requirement

> The app uses IPC mechanisms securely.

## Common Failure Patterns

- Exporting components without permissions or caller checks.
- Accepting intents/URLs without validating scheme, source, and data.
- Returning sensitive data to unauthenticated callers.

## Secure Implementation

Keep components non-exported by default, add permission guards and caller checks, and validate scheme/host/data for URL and deep-link handlers.

## Key Rules

- Keep components private (non-exported) by default.
- Authenticate and authorize every IPC caller.
- Validate all data crossing the IPC boundary.

## Checklist for Code Review

- Are exported components minimized and guarded?
- Is every caller authenticated/authorized?
- Is deep-link/URL input validated?
